# 小车工程完整使用分支与调用链说明

本文按“外部如何触发 -> 字节如何进入 TI 板 -> 哪个函数解析 -> 调用了什么业务模块 -> 周期任务怎样真正执行 -> 怎样回包或观察结果”的顺序解释当前工程。

本文以现行源码为准。板载捕获（`X` 命令、`Capture.c/.h`）已整体移除，见 15 节。仓库中的 `README.md` 有若干段落仍描述旧版本的 K230、F32C 或 CSV 遥测行为，不能仅凭“文件还存在”判断某个功能已经接入当前程序。

## 1. 当前程序到底运行了什么

当前 `main.c` 的有效入口只有一套：

```c
App_Init();
Mission_Init(Accomplish25H_GetMissionGraph());
Interrupt_Enable();

for (;;)
{
    if (App_Update(&updateContext) != 0U)
    {
        Mission_Update(&updateContext);
    }
}
```

对应源码：

- `main.c:6-20`：程序入口和永久循环。
- `Application/Core/App.c:131-170`：整车初始化。
- `Application/Core/App.c:172-288`：100 Hz 固定更新。
- `Accomplish/25H.c:233-242`：当前装载的 25H 状态图。

当前通信资源实际分配如下：

| 通道 | 当前用途 | 当前协议 | 关键模块 |
|---|---|---|---|
| UART1，PB6/PB7 | 无线 DAPLink 与电脑网页 | ASCII 命令、ASCII 回应、`0xAA` 二进制遥测 | `Serial1`、`BluetoothDebug`、`Telemetry` |
| UART2，PA21/PA22 | 两车 HC05 主从链路 | `CarLink` 控制帧、`0xAB` 从车遥测帧 | `Serial2`、`CarLink` |
| UART2 上的 K230/F32C | 当前停用 | 源码保留，运行入口被注释 | `K230Link`、`F32C`、`Gimbal` |

主从身份是编译期选择，见 `Application/Core/CarRole.h:19-31`。默认值是 `CAR_ROLE_MASTER`。烧录从车时必须改为 `CAR_ROLE_SLAVE` 或通过编译选项定义。

## 2. 所有网页命令共用的主干

### 2.1 网页发送

网页连接入口是 `car_debug.html:1768` 的 `connect()`：

1. `navigator.serial.requestPort()` 弹出串口选择框。
2. `port.open()` 使用 115200 baud、8 data bits、1 stop bit、no parity。
3. `port.writable.getWriter()` 获取写端。
4. 启动 `readLoop()` 持续读取回包和遥测。
5. 自动准备当前调参页面需要的遥测掩码和频率。
6. 300 ms 后自动发送 `K?` 拉取参数表。

所有普通网页命令最终都经过 `car_debug.html:1896` 的：

```js
async function send(cmd) {
    const line = cmd.trim();
    await writer.write(new TextEncoder().encode(line + '\r\n'));
}
```

因此点击 F 按钮并输入 500，实际发出的不是抽象的“F 命令”，而是 6 个字节：

```text
0x46 0x35 0x30 0x30 0x0D 0x0A
  F    5    0    0   \r   \n
```

### 2.2 UART1 中断只收字节，不执行命令

UART1 RX 到来后进入 `Hardware/Comms/Serial.c:340` 的 `UART1_IRQHandler()`。

中断处理流程：

```text
UART RX FIFO 有数据
  -> DL_UART_Main_receiveData()
  -> 写入 s_rxBuffer[writeIndex % 1024]
  -> writeIndex++
  -> 若未读数据超过 1024 字节，推进 readIndex，丢弃最旧字节
  -> Serial1_RxFlag = 1
```

重要边界：

- RX 使用中断，不使用 DMA。
- ISR 不知道字节是 F、5、0、0，也不会直接调用电机。
- 环形缓冲容量为 1024 字节，见 `Hardware/Comms/Serial.h:13`。
- 主循环长时间不运行且输入超过容量时，保留最新 1024 字节，旧数据被覆盖。

### 2.3 100 Hz 主循环读取并解析

`SysTick_Handler()` 每 10 ms 增加 tick，`Tick_PollCount()` 由 `App_Update()` 取走。没有 tick 时主循环执行 `__WFI()` 等待中断。

每个有效更新拍，`App_Update()` 的关键顺序是：

```text
Heading_Update
Odometry_Update
CarLink_Update
BluetoothDebug_Update
弹出 C 命令事件 / 处理 KEY2 急停
处理 CarLink 对端消息
MotionManager_Update
Telemetry_Update
Mission_Update（回到 main.c 后调用）
```

这个顺序带来三个重要结果：

1. 本拍运动控制使用的是本拍刚更新的航向和编码器速度。
2. 本拍收到的 F/T/J 等命令可以在同一拍进入 `MotionManager_Update()`。
3. `Telemetry_Update()` 放在运动更新之后，发出的是本拍新目标和新 PWM，不是上一拍的值。

### 2.4 BluetoothDebug 字节状态机

`Application/Comms/BluetoothDebug.c:940` 的 `BluetoothDebug_Update()` 循环调用：

```c
while (Serial1_ReadByte(&byte) != 0U)
{
    BluetoothDebug_ProcessByte(byte);
}
```

当前合法命令字母共 23 个：

```text
L R U C O D G M V F B T A Z P K W N E Y X Q J
```

另有主车专用的 `@` 前缀，它不是普通命令字母，而是进入 CarLink 转发收集模式。

通用整数命令解析规则：

- 小写字母先转大写。
- 数字按十进制累积，内部幅值最大累计到 1,000,000，防止溢出。
- `+` 或 `-` 只能出现在命令之后、第一位数字之前。
- `\r`、`\n`、空格、逗号、分号和 Tab 都是结束符。
- 没有结束符时，连续空闲 3 个系统拍，也就是约 30 ms 后执行。
- 新命令字到来时，如果旧命令尚未执行，会先执行旧命令。因此 `F500B200` 可以连续解析。
- 裸数字会回 `ERR COMMAND`。
- 普通命令缺少数字会回 `ERR FORMAT`。
- 非法字符会丢弃当前半条命令并回 `ERR CHARACTER`。
- `Q` 是唯一允许不带数字的普通查询命令。
- `K` 和 `J` 使用独立文本参数缓冲，因为它们分别需要处理 `.= ?` 和 `/`。

命令最终进入 `Application/Comms/BluetoothDebug.c:283` 的 `BluetoothDebug_ExecuteCommand()`，再按命令字分派。

### 2.5 回包如何返回网页

业务模块通常使用：

```c
Serial1_SendString("OK...\r\n");
Serial1_Printf("ERR...\r\n", ...);
```

`Serial1_SendArray()` 把完整数据写进 2048 字节 TX 环形缓冲，然后启动 DMA：

```text
主循环写 TX 环形缓冲
  -> Serial1_StartTxDma
  -> DMA 将连续区间搬到 UART1 TXDATA
  -> UART DMA_DONE_TX 中断
  -> Serial1_OnDmaTxComplete 推进 tail
  -> 若还有数据，立即启动下一段 DMA
```

缓冲空间不足时整段数据被丢弃，不会只发送半帧。ASCII 回应和二进制遥测共用这条 TX DMA 队列。

网页 `readLoop()` 收到 `Uint8Array` 后不会直接整体做 `TextDecoder`，而是交给 `routeStream()`：

- `0xAA 0x55`：主车二进制遥测帧。
- `0xAB 0x55`：从车二进制遥测帧。
- 其他可打印字节：ASCII 文本回应。

文本行最终由 `car_debug.html:1715` 的 `handleTextLine()` 处理并显示。

## 4. 分支一：V、F、B 直线定距

### 4.1 使用方式

```text
V300    设置后续 F/B/T/A 使用的调试速度为 300 mm/s
F500    按当前调试速度前进 500 mm，终点速度为 0
B500    按当前调试速度后退 500 mm，终点速度为 0
```

网页运动面板定义在 `car_debug.html:249-287`。距离输入框默认值就是 500，点击 F 按钮时通用事件处理器执行：

```js
send(btn.dataset.send + $(btn.dataset.from).value)
```

### 4.2 F500 从接收到启动的完整调用链

```text
网页 F 按钮
  -> send("F500")
  -> writer.write("F500\r\n")
  -> DAPLink 串口桥
  -> UART1 RX
  -> UART1_IRQHandler
  -> Serial1 RX 环形缓冲
  -> App_Update
  -> BluetoothDebug_Update
  -> BluetoothDebug_ProcessByte('F','5','0','0','\r')
  -> BluetoothDebug_StartCommand
  -> BluetoothDebug_ExecuteCommand
  -> case 'F'
  -> BluetoothDebug_RejectIfBusy
  -> MotionManager_StartForward(500, s_debugSpeedMMps, 0)
  -> MotionStraight_StartForward
  -> MotionStraight_Start
  -> MotionManager 模式设为 STRAIGHT
```

关键源码：

- `Application/Comms/BluetoothDebug.c:442-451`：V 修改 `s_debugSpeedMMps`。
- `Application/Comms/BluetoothDebug.c:453-466`：F 校验和启动。
- `Application/Comms/BluetoothDebug.c:468-481`：B 校验和启动。
- `Application/Control/MotionManager.c:173-208`：统一运动入口。
- `Application/Control/MotionStraight.c:376-438`：直线动作初始化。

### 4.3 启动前检查

F/B 必须满足：

- `MotionManager_IsBusy() == 0`，否则 `ERR BUSY`。
- 距离为 1 到 10000 mm，否则 `ERR RANGE`。
- `s_debugSpeedMMps` 由 V 设置，范围 20 到 800 mm/s，默认 200。
- `MotionStraight` 已初始化。
- `Heading_IsReady() != 0`，即 MPU6050 航向可用。
- `Odometry_CountsPerMM > 0.001`，编码器比例有效。

如果传感器未准备好，`MotionManager_StartForward()` 返回 `MOTION_MANAGER_RESULT_SENSOR_NOT_READY`，外层打印：

```text
ERR MOTION 3
```

### 4.4 MotionStraight 保存了什么

动作启动时 `MotionStraight_Start()`：

- 停止并复位轮速控制器。
- 记录左右编码器当前累计距离作为起点。
- 记录 `Heading_GetYaw()` 作为本次直线目标航向。
- 保存带符号总距离。F 为正，B 通过 `MotionStraight_StartBackward()` 转成负距离。
- 保存巡航速度、终点速度和速度规划状态。
- 状态进入 `MOTION_STRAIGHT_STATE_RUNNING`。

### 4.5 每个 10 ms 控制拍真正做什么

`MotionManager_Update()` 在 STRAIGHT 模式调用 `MotionStraight_Update(dt)`：

1. 从 `Odometry_GetDistanceLMM/RMM()` 计算相对起点的左右轮位移。
2. 根据行驶方向和左右轮平均位移计算已走距离、剩余距离。
3. 根据加速度、最大巡航速度、减速区和终点速度生成当前目标速度。
4. 使用航向 PID：目标是启动时记录的航向，测量是 `Heading_GetYaw()`。
5. PID 输出变成左右轮相反方向的 trim PWM，用于纠偏。
6. 两轮基础目标速度相同，交给 `MotionWheel_Update()`。

当前默认参数包括：

- 航向 Kp 6.0、Kd 0.4。
- 航向修正上限 700 PWM。
- 起步加速度 300 mm/s²。
- 距离容差 5 mm。
- 到点后短接刹车保持 0.08 s。

`MotionWheel_Update()` 再对每个轮执行：

```text
目标速度
  -> 速度前馈 target * ff
  -> 加 sign(target) * 静摩擦补偿
  -> 加 PI(target - encoderSpeed)
  -> 加直线航向 trim
  -> 限制到 ±1000
  -> Motor_SetPWM
```

`Motor_SetPWM()` 最终写左右电机方向 GPIO 和 TIMER PWM compare。

### 4.6 完成、回包和可观察结果

启动成功时立即执行：

```c
Serial1_SendString("OK\r\n");
```

所以 `OK` 只表示“成功启动”，不是“已经走完”。当前固件在 F/B 完成时不主动发送另一条文本 DONE。

可以通过遥测观察：

- `TL/TR`：左右目标轮速。
- `LV/RV`：编码器实测轮速。
- `PL/PR`：最终输出 PWM。
- `yaw`：航向是否保持。
- `LD/RD`：左右累计里程。

到达目标后，直线模块完成减速和刹车，`MotionStraight_IsFinished()` 变为真。网页调参会用 LD/RD 接近目标且轮速接近 0 作为完成判据，而不是等待文本 DONE。

## 5. 分支二：T、A 转向

### 5.1 两种参考系

```text
T90     从当前航向再增加 90°
T-90    从当前航向再减少 90°
A90     转到连续航向空间中的绝对 90°
```

解析入口：

- `Application/Comms/BluetoothDebug.c:483-496`：T。
- `Application/Comms/BluetoothDebug.c:498-511`：A。

调用链：

```text
T -> MotionManager_TurnBy -> Nav_StartBy
A -> MotionManager_TurnTo -> Nav_StartTo
  -> MotionManager 模式 TURN
  -> 每拍 Nav_Update
  -> MotionWheel_Update
  -> Motor_SetPWM
```

### 5.2 T 与 A 的实际目标计算

`Nav_StartBy(delta)` 最终调用：

```c
Nav_StartTo(Heading_GetYaw() + delta);
```

`Nav_StartTo(target)` 直接把 target 保存为连续绝对目标。Nav 不做 `[-180,+180]` 最短路径归一化。

例如当前连续航向为 370°：

- `A90` 的误差是 `90 - 370 = -280°`，会按 -280° 路径转。
- 若希望走最短的 +80°，上位机应发送 `T80`。

### 5.3 每拍转向控制

`Nav_Update()` 每拍：

1. 计算 `angleError = targetYaw - Heading_GetYaw()`。
2. 按误差大小在最大转速、减速区、最低转速之间生成转向速度。
3. 用加速度 150 mm/s²、减速度 600 mm/s²平滑改变目标。
4. 设置 `leftTarget = turnSpeed`、`rightTarget = -turnSpeed`，原地转向。
5. 进入默认 ±2° 容差后将目标速度收敛到 0。
6. 连续稳定 3 拍，也就是约 30 ms 后进入 COMPLETED。

T/A 允许 -3600 到 +3600 度。动作忙、MPU 离线、参数无效时分别返回 `ERR BUSY`、`ERR MOTION 3` 或其他 `ERR MOTION <code>`。

和 F/B 一样，成功只立即回 `OK`。

## 6. 分支三：W 恒速阶跃

### 6.1 用途和调用链

```text
W300     左右轮闭环目标都设为 +300 mm/s
W-300    左右轮闭环目标都设为 -300 mm/s
W0       退出恒速模式并释放电机
```

入口是 `Application/Comms/BluetoothDebug.c:555-597`：

```text
case W
  -> MotionManager_StartSpeed(value)
  -> 模式 SPEED
  -> MotionManager_Update 每拍构造左右同目标的 MotionWheel_Command
  -> MotionWheel_Update
  -> Motor_SetPWM
```

### 6.2 与 F 的区别

W 不经过 `MotionStraight`，因此没有：

- 目标距离；
- 加减速规划；
- 航向保持 PID；
- 自动完成条件。

W 是给轮速 PI 做阶跃测试的持续模式。已经处于 SPEED 模式时再发送 W，只修改 `speedTargetMMps`，不会复位左右轮 PID，适合连续做 `W100 -> W300 -> W500`。

### 6.3 停止规则

`W0` 只允许在当前模式是 SPEED 或 IDLE 时执行。如果 25H、F、T、N 或 J 正在运行，W0 返回 `ERR BUSY`，不会越权停止其他动作。全局停止应使用 C0。

非零 W 的协议范围是 -800 到 +800 mm/s。成功回 `OK W=<value>`。

## 7. 分支四：N 五路灰度巡线

### 7.1 调用链

```text
N200
  -> BluetoothDebug case N
  -> MotionManager_StartLine(200)
  -> MotionLine_Start
  -> 模式 LINE
  -> 每拍 MotionLine_Update
  -> Graydetect_GetState
  -> 计算左右目标速度
  -> MotionWheel_Update
  -> Motor_SetPWM
```

入口见 `Application/Comms/BluetoothDebug.c:599-642` 和 `Application/Control/MotionLine.c:193-248`。

### 7.2 灰度位和权重

五路灰度从左到右为 bit0 到 bit4，检测到黑线返回 1：

| 探头 | 位 | 权重贡献 |
|---|---:|---:|
| 最左 | bit0 | -6 |
| 左内 | bit1 | -3 |
| 中间 | bit2 | 0 |
| 右内 | bit3 | +3 |
| 最右 | bit4 | +6 |

同侧多探头同时压线时，最终权重仍限制在 -6 到 +6。

速度修正近似为：

```text
adjust = cruiseSpeed * lra * weight / 6
       + lkd * (weight - previousWeight) / dt

leftTarget  = cruiseSpeed + adjust
rightTarget = cruiseSpeed - adjust
```

源码见 `Application/Control/MotionLine.c:72-170`。

### 7.3 丢线和停止

灰度状态为 0 时：

- 短暂丢线继续沿用上一拍左右目标速度。
- 连续 50 个控制拍全白，也就是约 0.5 s，确认丢线。
- `MotionLine` 停止轮速控制并进入 FINISHED。

N0 只允许停止 LINE 或 IDLE 模式，其他模式返回 `ERR BUSY`。非零 N 范围是 20 到 800 mm/s，成功回 `OK N=<value>`。

## 8. 分支五：J 左右轮差速驾驶

### 8.1 网页如何生成 J

主车键盘驾驶使用 WASD。`car_debug.html:3252` 的 `driveVector()` 计算：

```text
throttle = W - S
steer    = D - A
base     = throttle * driveSpeed
bias     = steer * turnSpeed
left     = clamp(base + bias, -800, 800)
right    = clamp(base - bias, -800, 800)
```

`applyDrive()` 发送：

```text
J<left>/<right>
```

例如：

- 只按 W：`J250/250`，直行。
- 只按 D：`J150/-150`，原地转向。
- W+D：`J400/100`，走弧线。
- 全部松开：`J0/0`。

网页用 `lastDriveSent` 去重，相同左右目标不会重复发送；窗口失焦时也会补发停车，防止浏览器收不到 keyup。

### 8.2 J 使用独立文本解析

J 不能使用普通的单整数累加器，因为参数包含两个带符号整数和 `/`。解析路径是：

```text
BluetoothDebug_ProcessByte
  -> command == J 时收集数字、负号和 '/'
  -> BluetoothDebug_ExecuteCommand
  -> BluetoothDebug_HandleDrive(textArgs)
  -> BluetoothDebug_ParseInt(left)
  -> 检查 '/'
  -> BluetoothDebug_ParseInt(right)
```

格式错误回 `ERR J FORMAT`，任一轮超出 ±800 回 `ERR RANGE`。

### 8.3 执行和连续更新

只有以下两种状态接受 J：

- MotionManager 空闲；
- 已经处于 DRIVE 模式。

其他任务正在控制轮子时返回 `ERR BUSY`。

非零命令调用：

```c
MotionManager_SetDrive(leftMMps, rightMMps);
```

第一次进入 DRIVE 时停止旧模式并保存左右目标。已在 DRIVE 时只更新目标，不复位两个轮速 PID，因此适合高频键盘/摇杆控制。

每拍 `MotionManager_Update()` 直接构造左右不同目标的 `MotionWheel_Command_t`，不经过 `MotionStraight`、`Nav` 或 `MotionLine`。

`J0/0` 调用 `MotionManager_Stop()`，成功回 `OK J=0/0`。其他成功命令回 `OK J=<left>/<right>`。

（板载捕获已移除，原先此处关于 J 不触发 `Capture_Trigger()` 的差异说明不再适用。）

## 9. 分支六：L、R、U 开环 PWM

```text
R300     只改右轮 PWM
U300     左右轮都设为 300
```

```c
manualMotorEnabled = (MotionManager_IsBusy() == 0);
```

## 10. 分支七：C 任务信号、C0 全局急停和 KEY2

### 10.1 C 命令不是普通运动命令

```text
C0       全局停车并让 Mission 回到起始状态
C1..255  向 Mission 提供一拍任务事件
```

`Application/Comms/BluetoothDebug.c:371-390` 不直接启动某个动作，而是调用：

```c
BluetoothDebug_PublishSignal((uint8_t)value);
```

内部只有一个槽：

- 普通信号不排队；在 Mission 取走之前，新普通信号覆盖旧普通信号。
- C0 具有最高优先级；C0 待处理时，后续普通信号不能覆盖它，并返回 `ERR STOP PENDING`。
- 发布成功回 `OK C=<value>`。

### 10.2 App 如何消费信号

同一拍 `BluetoothDebug_Update()` 结束后，`App_Update()` 调用：

```c
BluetoothDebug_PopSignal(&context->bluetoothSignal);
```

然后把结果放进 `App_UpdateContext_t`：

```text
hasBluetoothSignal
bluetoothSignal
```

若信号为 0，App 不等待 Mission，立刻执行：

```c
MotionManager_Stop();
Motor_StopAll();
```

随后 `main()` 调用 `Mission_Update()`。`Application/Mission/Mission.c:217-220` 再识别信号 0，执行 `Mission_ResetToStart()`，从题目状态图回到 startState。

这就是 C0 的两层保障：

1. App 层立即释放运动控制和电机，不依赖状态图是否可打断。
2. Mission 层清理当前状态，保证下次从等待状态重新开始。

### 10.3 KEY2 与网页急停

KEY2 在按键位图中是 bit1。`Application/Core/App.c:213-220` 把 KEY2 的按下沿合成为：

```text
hasBluetoothSignal = 1
bluetoothSignal = 0
```

所以车载物理急停和 C0 使用完全相同的 App/Mission 停车路径。

网页红色急停按钮不是只发一条 C0。`car_debug.html:2807` 的 `emergencyStop()` 依次发送一组去重后的命令：

```text
当前调参动作的 stopCmd（如果有）
J0/0
@J0/0
W0
N0
C0
U0
```

这样既清网页的主车/从车键盘状态，也尝试退出各种持续模式，最终由 C0 兜底全局停止。

### 10.4 C1..C255 在当前 25H 中的效果

当前 25H 状态图的启动条件只检查 KEY1 的 `pressedEdges`，没有检查 `bluetoothSignal == 1`。因此：

- C1..C255 会被正确发布并进入本拍 `App_UpdateContext_t`。
- 当前 25H 没有消费它们，Mission 本拍结束后信号即消失。
- C1 当前不能代替 KEY1 启动 25H。
- 要绑定某个 C 信号，应在题目状态图的 condition callback 中调用 `Mission_ContextHasBluetoothSignal()`。

### 10.5 主车还会把 C 事件同步给从车

默认主车编译中，只要本机本拍存在 C 信号或 KEY2 急停，App 还会调用：

```c
CarLink_SendEvent(context->bluetoothSignal, NULL, 0U);
```

这个主从事件分支在第 17 节详细说明。

## 11. 分支八：Z、E、Y 航向基准和陀螺仪标定

### 11.1 Heading 数据从哪里来

`Heading_Init()` 初始化 MPU6050，`Heading_Calibrate()` 在开全局中断前采集静止零漂。之后每个 App 更新拍先调用：

```c
Heading_Update(dt);
```

它读取 MPU6050 Z 轴角速度，减去 bias，再乘 scale 和 dt，积分为连续航向 `s_yaw`。航向不会自动限制在 ±180°。

### 11.2 Z1：只改角度基准

```text
Z1
  -> BluetoothDebug case Z
  -> 检查 MotionManager 空闲
  -> Heading_SetYaw(0.0f)
  -> OK Z=1
```

Z1 不重新估计零漂，也不修改尺度系数。适合在已知方向地标处把当前方向定义为 0°。

### 11.3 Z2：重新采静止零漂

```text
Z2
  -> 检查运动空闲
  -> Heading_IsReady
  -> 检查没有正在做 E/Y 尺度标定
  -> Heading_Calibrate
  -> OK Z=2 或 ERR Z OFFLINE
```

`Heading_Calibrate()` 连续采样 MPU6050 Z 轴，计算新的 bias，并把航向归零。该函数会阻塞约 0.8 秒，车辆必须完全静止，否则会把真实转动误认为零漂。

错误包括：

- `ERR BUSY`：运动正在运行。
- `ERR Z OFFLINE`：MPU6050 不在线或采样中掉线。
- `ERR Z CALIBRATING`：E/Y 尺度标定正在进行。
- `ERR RANGE`：Z 参数不是 1 或 2。

### 11.4 E/Y：陀螺仪尺度标定

尺度标定用于修正“传感器积分 360°，实车实际没有正好转一圈”的比例误差。

流程：

```text
车辆静止且 MotionManager 空闲
  -> E1
  -> Heading_ScaleCalibStart，清零标定累计角
  -> 手工或开环方式原地转 N 个完整圈并回到起始方向
  -> YN
  -> Heading_ScaleCalibFinish(N)
  -> 计算并应用新 scale
```

`E0` 调用 `Heading_ScaleCalibCancel()` 取消。

Y 接受 1 到 20 圈。成功回应：

```text
OK Y SCALE=<新尺度> RAW=<累计原始角>
```

错误：

- `ERR CAL OFFLINE`：E1 时 MPU 离线。
- `ERR CAL IDLE`：未执行 E1 就发送 Y。
- `ERR CAL SMALL`：累计角绝对值不超过 1°，说明没有实际转起来。
- `ERR RANGE`：E 不是 0/1，或 Y 圈数不在 1..20。

网页收到 OK Y 后，会把 SCALE 同步到参数表中的 `gsc` 项，但固件只在 RAM 中应用；要永久保存仍需把值写回源码默认参数或实现 Flash 保存。

## 14. 分支十一：M、G、Q 二进制遥测

### 14.1 三条上行 ASCII 命令

```text
M63    选择 TL/LV/PL/TR/RV/PR 六个通道
G50    以 50 Hz 发送实时遥测
G0     停止实时遥测
Q      查询当前遥测能力
```

M 范围是 1..4095。通道位定义：

| bit | 十六进制 | 名字 | 数据来源 |
|---:|---:|---|---|
| 0 | 0x001 | TL | `MotionWheel_GetTargetSpeedL()` |
| 1 | 0x002 | LV | `Odometry_GetSpeedL()` |
| 2 | 0x004 | PL | `MotionWheel_GetLeftCommandPWM()` |
| 3 | 0x008 | TR | `MotionWheel_GetTargetSpeedR()` |
| 4 | 0x010 | RV | `Odometry_GetSpeedR()` |
| 5 | 0x020 | PR | `MotionWheel_GetRightCommandPWM()` |
| 6 | 0x040 | yaw | `Heading_GetYaw()`，离线时为无效 float |
| 7 | 0x080 | navE | `Nav_GetAngleErrorDeg()`，离线时无效 |
| 8 | 0x100 | lerr | `MotionLine_GetLineError()` |
| 9 | 0x200 | gray | `Graydetect_GetState()` 转 float |
| 10 | 0x400 | LD | `Odometry_GetDistanceLMM()` |
| 11 | 0x800 | RD | `Odometry_GetDistanceRMM()` |

`Telemetry_SetFieldMask()` 更新掩码后置 `s_schemaPending=1`。如果当前频率超过新帧长度允许的上限，会自动降频。

G 的硬上限是 100 Hz，但还受当前帧长度和 115200 波特率限制。当前代码按 70% 串口带宽预算计算：

```text
sampleFrameBytes = 7 + 4 + channelCount * 4
maxRate = floor((11520 * 70%) / sampleFrameBytes)
maxRate 最终限制在 1..100
```

G0 是特殊合法值，用于关闭实时流。超限回：

```text
ERR RANGE MAX=<当前掩码允许的最高频率>
```

还要注意当前发送节拍不是任意频率的精确分数累加器，而是：

```c
interval = TELEMETRY_TICK_HZ / s_rateHz;  // 整数除法
```

正常每拍进入一次 Update 时，实际频率近似为 `100 / floor(100 / G值)`。因此 50、25、20、10 Hz 这类 100 的约数能准确输出；`G30` 实际约为 33.3 Hz，`G60`、`G99` 都会变成每拍一次，也就是约 100 Hz。`Telemetry_GetRateHz()` 和 Q 回包仍显示请求值 30/60/99，不显示这个量化后的实际值。若实际频率高于按请求值做的带宽预期，TX 缓冲更容易丢帧。这是现行实现行为，若要支持任意整数 Hz，应改成相位累加方式。

Q 不带参数，回应：

```text
OK Q MAX=<hz> MASK=<mask> RATE=<hz> CAPST=<state> CAPN=<count> CAPMAX=<capacity>
```

### 14.2 固件怎样构建遥测帧

`Application/Debug/Telemetry.c:255-281` 的 `Telemetry_Update()` 每拍累积时间和发送节拍。到发送时刻：

1. 掩码刚变化时先调用 `Telemetry_SendSchema()`。
2. 再调用 `Telemetry_SendSample()`。
3. `TelemFrame_Build()` 加帧头、序号、长度和 CRC。
4. 主车 `Telemetry_Emit()` 走 `Serial1_SendArray()`。
5. 从车改首字节为 0xAB，走 `Serial2_SendArray()`。

统一二进制帧格式：

```text
BYTE 0   0xAA（主车）或 0xAB（从车）
BYTE 1   0x55
BYTE 2   VERSION = 0x01
BYTE 3   TYPE
BYTE 4   SEQUENCE，uint8 自然回绕
BYTE 5   PAYLOAD LENGTH
BYTE 6.. PAYLOAD
最后     CRC-8/ATM，多项式 0x07
```

CRC 覆盖 VERSION、TYPE、SEQUENCE、LENGTH 和 PAYLOAD，不覆盖两个 magic 字节。

实时帧类型：

- `0x30 SCHEMA`：payload 先放 mask:u16_LE，随后每个通道放 `nameLen:u8 + name bytes + unit:u8`。
- `0x31 SAMPLE`：payload 为 `ms:u32_LE + 每个选中通道 float32_LE`。

### 14.3 网页怎样解析并使用

`car_debug.html:4080` 的 `routeStream()` 先按完整帧分流：

- 0xAA 帧交给主车 `parser`。
- 0xAB 帧把首字节归一化为 0xAA 后交给 `slaveParser`。
- 其他字节交给主车文本解析。

`car_debug.html:584` 的 `TelemetryParser` 状态机依次经过：

```text
idle -> magic1 -> header -> payload -> crc
```

CRC 正确后：

- SCHEMA 重建列名、单位和图例，并清空与旧列定义不兼容的样本。
- SAMPLE 用 `DataView.getUint32(..., true)` 和 `getFloat32(..., true)` 按小端读取。
- 非有限 float 不写入样本对象，所以 MPU 离线时网页对应字段为空，不会误显示 0。
- 序号跳变或 CRC 错误会增加 `droppedFrames`。
- 样本进入曲线、调参指标、录制和 CSV 导出流程。

## 15. 分支十二：X 板载捕获（已移除）

`X` 命令、`Application/Debug/Capture.c/.h`、`CAP_META`/`CAP_SAMPLE`/`CAP_END`
三种帧类型，以及 `Q` 回应里的 `CAPST`/`CAPN`/`CAPMAX` 三个字段，均已整体删除。

**为什么删。** 捕获在 ASCII 双通道架构下引入，理由是"实时流 30 Hz 低于 100 Hz
控制环"。二进制 + DMA 之后实时流本身就是 100 Hz 无损直传，捕获只剩两个边缘用途
（录得比串口实时率更久、绝对零丢包），代价却是 `s_buffer[24576]` 独占 32 KB SRAM
的 75%。

**它引发过一次整车卡死。** `.stack` 由 SysConfig 硬编码为 512 字节、置于 SRAM 顶部
向下生长，紧邻其下就是 `.data`。启用 K230（Serial3 收发缓冲各 256 字节）后，栈可用
余量被压到 1587 字节，而实测最深调用链约 1900 字节
（`App_Update` 208 + `Telemetry_Update` 592 + `SendSchema` 552，或
`Capture_DumpNext` 296 + `Serial1_Printf` 216 + `__TI_printfi` 584 + `_pconv_f` 552）。
栈越界自顶向下改写 `.data`：

- `Heading.o (.data.s_scale)` → yaw 增量恒为 0，OLED 上 z 轴数值固定
- `Odometry.o (.data.Odometry_CountsPerMM / s_distanceL/R / s_speedL/R)` → `LD/RD/LV/RV` 恒为 0
- `Nav_Tune*` / `MotionWheel_Tune*` / `MotionStraight s_context` → 增益与状态机失效，车不动
- `Graydetect.o` 对 `.data` 零贡献 → 灰度不受影响，照常刷新

删除后 SRAM 占用从 31693/32768（96.7%）降到 7102/32768（21.7%），栈可用余量
26175 字节。历史实现在 `fix/ram-stack-overflow` 分支删除该模块的提交之前可取。

**对以后仍然适用的教训。** 新增任何大型静态缓冲，都要同时核对
`Debug/ArcLineTest.map` 里 `.data` 末尾到 `.stack` 之间还剩多少空隙——那才是栈真正
能用的空间。`--stack_size` 由 SysConfig 按器件硬编码生成到 `device_linker.cmd`
（本器件 512），既不在 `main.syscfg` 里、手工改了也会被下次构建覆盖，指望链接器
报错是靠不住的。

## 16. 分支十三：`@<command>` 主车转发命令到从车

这一分支不是增加一套从车专用命令，而是把现有 `BluetoothDebug` 命令完整复用到另一块 TI 板。以网页发送 `@F500` 为例，整条链路跨越两块板和三段串口：

```text
网页
  -- Web Serial / UART1 --> 主车 TI
  -- UART2 / HC05 -------> 从车 TI
  -- UART2 / HC05 -------> 主车 TI
  -- UART1 / Web Serial -> 网页
```

### 16.1 使用前提：两块板必须烧不同角色的固件

`Application/Core/CarRole.h:19-31` 定义编译期角色：

```c
#define CAR_ROLE_MASTER 1
#define CAR_ROLE_SLAVE  2

#ifndef CAR_ROLE
#define CAR_ROLE CAR_ROLE_MASTER
#endif
```

默认编译结果是主车。烧从车时必须把 `CAR_ROLE` 改为 `CAR_ROLE_SLAVE`，或在从车工程的编译选项中定义 `-DCAR_ROLE=CAR_ROLE_SLAVE`。角色会决定：

- 主车的 `BluetoothDebug_ProcessByte()` 是否识别 `@`。
- 从车的 `App_HandlePeerMessage()` 是否执行 `RELAY_CMD`。
- 主车的 `App_HandlePeerMessage()` 是否把 `RELAY_REPLY` 输出给网页。
- 从车遥测走 UART2 还是主车遥测走 UART1。

两块板如果都烧成默认主车，UART2 的底层帧仍可能互相收到，但对方不会进入“执行转发命令”的从车分支。

### 16.2 网页实际发送的字节

网页 `send('@F500')` 调用 `TextEncoder` 并追加 `\r\n`，UART1 上实际字节为：

```text
字符： @  F  5  0  0  \r \n
十六进制：40 46 35 30 30 0D 0A
```

主车 UART1 RX 中断仍只把字节写入 `Serial1` 环形缓冲。100 Hz 主循环中的 `BluetoothDebug_Update()` 再调用 `Serial1_ReadByte()` 逐字节取出。

### 16.3 主车怎样识别并收集 `@F500`

`Application/Comms/BluetoothDebug.c:794-825` 的处理过程是：

```text
收到 '@'，且当前没有普通命令
  -> BluetoothDebug_ResetParser()
  -> relayMode = 1

继续收到 F、5、0、0
  -> 全部经 BluetoothDebug_ToUpper()
  -> 写入 textArgs[]

收到 '\r'
  -> BluetoothDebug_FinalizeRelay()
```

空格、逗号、分号、Tab、CR、LF 都会结束转发命令；没有结束符时，空闲 3 个系统拍，也就是约 30 ms 后收尾。

转发收集缓冲 `BLUETOOTH_TEXT_ARGS_SIZE` 是 24 字节，必须给 `\0` 留一字节，所以网页 `@` 后面最多只能放 23 个字符。虽然 CarLink 载荷允许 32 字节，但当前入口先受这个 23 字符限制。

`BluetoothDebug_FinalizeRelay()` 的行为是：

```text
textOverflow != 0 -> ERR @ FORMAT
textLength == 0   -> ERR @ EMPTY
其他              -> textArgs 末尾补 '\0'
                   -> CarLink_SendCommand(textArgs)
```

### 16.4 主车怎样把 ASCII 命令封装成 CarLink 帧

`CarLink_SendCommand("F500")` 计算字符串长度 4，再调用：

```c
CarLink_Send(CAR_LINK_MSG_RELAY_CMD,
             (const uint8_t *)"F500", 4U);
```

UART2 上的帧布局为：

```text
AA 55 | 01 | 10 | SEQ | 04 | 46 35 30 30 | CRC
```

字段含义：

| 字段 | 本例值 | 含义 |
|---|---:|---|
| MAGIC | `AA 55` | CarLink 控制帧头 |
| VER | `01` | 协议版本 |
| TYPE | `10` | `RELAY_CMD` |
| SEQ | 自动递增 | 8 位发送序号，自然回绕 |
| LEN | `04` | ASCII 载荷 4 字节 |
| PAYLOAD | `46 35 30 30` | ASCII `F500`，不含 `@`、CR、LF 和 `\0` |
| CRC | 运行时计算 | CRC-8/ATM，覆盖 VER 到 PAYLOAD |

`CarLink_SendFrame()` 最后调用 `Serial2_SendArray()`。Serial2 把整帧写入 512 字节 TX 环形缓冲，再由 UART2 DMA 分段发送；空间不足时整帧丢弃，不会发送半帧。

这里有一个容易误判的实现细节：`CarLink_SendFrame()` 在 Serial2 缓冲满时只增加 `s_txDropCount`，但 `CarLink_Send()` 仍返回 1。因此主车打印：

```text
OK @F500
```

只表示转发命令格式合法并走到了 CarLink 发送入口，不表示：

- 对端当前在线；
- UART2 帧一定进了 DMA 缓冲；
- 从车已经收到；
- 从车已经成功启动 F500。

在当前 23 字符入口限制下，`ERR @ LINK` 实际上几乎不会由“掉线”产生，因为 `CarLink_SendCommand()` 不检查 `CarLink_IsPeerAlive()`，而且底层 TX 丢帧也没有向上传播。真正判断从车执行结果要等后面的 `SLV ...`。

### 16.5 从车 UART2 怎样收帧和解析

从车 `UART2_IRQHandler()` 从 UART2 RX FIFO 取字节，写入 `Serial2` RX 环形缓冲。下一拍 `App_Update()` 先调用 `CarLink_Update(elapsedTicks)`：

```text
Serial2_ReadByte
  -> CarLink_ParseByte
     MAGIC_0
     -> MAGIC_1
     -> VERSION
     -> TYPE
     -> SEQUENCE
     -> LENGTH
     -> PAYLOAD
     -> CRC
```

版本不等于 1、长度大于 32 或 CRC 错误都会复位解析器，不把消息交给上层。合法的心跳只刷新在线状态；合法的 `RELAY_CMD` 调用 `CarLink_Enqueue()` 进入 6 项消息队列。

队列满时不是拒绝新消息，而是丢掉最旧消息、保留最新消息。这对遥控实时性有利，但意味着持续高速发送时某条中间命令可能无通知地消失。

### 16.6 从车怎样复用本地命令解析器执行 `F500`

同一拍稍后，`App_Update()` 用 `CarLink_PopMessage()` 取出消息并调用 `App_HandlePeerMessage()`。从车的 `RELAY_CMD` 分支是：

```text
Serial1_BeginCapture(reply, 32)
  -> BluetoothDebug_FeedExternal(payload="F500", length=4)
     -> BluetoothDebug_ProcessByte('F')
     -> BluetoothDebug_ProcessByte('5')
     -> BluetoothDebug_ProcessByte('0')
     -> BluetoothDebug_ProcessByte('0')
     -> BluetoothDebug_ProcessByte('\n')  // 人工补终止符
  -> BluetoothDebug_ExecuteCommand()
  -> case F
  -> BluetoothDebug_RejectIfBusy()
  -> MotionManager_StartForward(500, debugSpeed, 0)
  -> Serial1_SendString("OK\r\n")
Serial1_EndCapture()
```

`Serial1_BeginCapture()` 之后，从车命令处理器所有本来要发往从车 UART1 的回应不再真正发送，而是写入 32 字节 `reply[]`。因此从车可以完全复用 `F/B/T/A/W/N/J/K/...` 的执行逻辑和错误检查，无需为 CarLink 再写一套命令分派。

`BluetoothDebug_FeedExternal()` 最后强制补一个换行，所以 CarLink 载荷不需要携带终止符。内层命令启动后，从车在 `App_HandlePeerMessage()` 之后继续执行本拍的 `MotionManager_Update()`，动作可在收到帧的同一系统拍生效。

### 16.7 从车回应怎样返回网页

从车捕获到 `OK\r\n` 后调用：

```c
CarLink_Send(CAR_LINK_MSG_RELAY_REPLY, reply, replyLen);
```

回帧类型是 `0x11`。主车下一拍解析并出队，在 `App_HandlePeerMessage()` 中输出：

```text
Serial1_SendString("SLV ");
Serial1_SendArray(msg->payload, msg->length);
```

最终网页终端看到两级回应：

```text
OK @F500       主车：已接受转发请求
SLV OK         从车：F500 已通过参数/忙状态/传感器检查并启动
```

如果从车正忙，则可能是：

```text
OK @F500
SLV ERR BUSY
```

如果 MPU/Heading 未就绪，则可能是：

```text
OK @F500
SLV ERR MOTION 3
```

所以判断业务动作必须使用第二行，而不能只看第一行。

### 16.8 哪些命令适合转发，哪些有局限

`@` 机制能转发全部现有命令，但不是每条都同样适合：

| 内层命令 | 可执行性 | 注意点 |
|---|---|---|
| `@F/@B/@T/@A/@W/@N/@J` | 适合 | 从车走与本地相同的 MotionManager 分支 |
| `@L/@R/@U` | 可用 | 仍受从车 `manualMotorEnabled` 和忙状态限制 |
| `@M/@G/@Q` | 可用 | `@M/@G` 控从车遥测；从车数据另走 `0xAB` 帧 |
| `@C0` | 可用 | 在从车本地发布 C0，下一拍由从车 App/Mission 完整执行全局停止和任务复位 |
| `@K17?`、`@K17=...` | 可用 | 单行短回应正常 |
| `@K?` | 不适合 | K? 有 27 行输出，而回应捕获区只有 32 字节，只会截取开头，不能得到完整参数表 |
| `@P1` | 当前不可用 | 从车也没有启用 K230Link，仍回 `SLV ERR CAP NOLINK` |

回应超过 32 字节会被 `Serial1_SendArray()` 的捕获模式静默截断。若被截断部分恰好包含行尾，主车加上 `SLV ` 后可能与后续文本粘在一起。要远程执行长查询，应新增分片消息，而不是扩大一处缓冲后假定问题已经解决。

### 16.9 本分支的关键源码

- `car_debug.html:1896-1907`：网页追加 CRLF 并写入 Web Serial。
- `Application/Comms/BluetoothDebug.c:114-140`：转发收尾与第一阶段回应。
- `Application/Comms/BluetoothDebug.c:794-825`：`@` 收集状态。
- `Application/Comms/BluetoothDebug.c:997-1015`：从车外部字节流重新喂入解析器。
- `Application/Comms/CarLink.c:128-166`：CarLink 封帧、CRC 和 Serial2 DMA 入队。
- `Application/Comms/CarLink.c:168-248`：逐字节解析器。
- `Application/Comms/CarLink.c:418-437`：`CarLink_SendCommand()`。
- `Application/Core/App.c:46-128`：从车执行、主车显示回应。
- `Hardware/Comms/Serial.c:122-211`：Serial1 输出捕获。

## 17. 分支十四：CarLink 心跳、掉线、EVENT 与 ACK

### 17.1 心跳和在线状态

主车和从车每次 `App_Update()` 都调用 `CarLink_Update(elapsedTicks)`。累计 50 个 100 Hz 系统拍后，双方各发送一次无载荷心跳：

```text
AA 55 | 01 | 01 | SEQ | 00 | CRC
```

收到任意 CRC 正确的 CarLink 控制帧都会执行：

```c
s_peerSilenceTicks = 0U;
s_peerAlive = 1U;
```

连续 200 拍，也就是约 2 秒没有收到合法帧，`s_peerAlive` 才变为 0。心跳不进入业务队列，避免每 0.5 秒唤醒一次 App 业务处理。

`CarLink_IsPeerAlive()` 当前只提供固件查询接口，`BluetoothDebug_FinalizeRelay()` 没有使用它，网页也没有直接查询它。网页“从车链路在线”是根据最近 2 秒是否收到 `0xAB` 遥测帧推断，所以：

- 从车 CarLink 心跳正常但 `@G0` 时，网页仍可能显示“无数据/未知”。
- 网页显示从车遥测在线，才同时证明从车到主车再到网页的数据通路有效。
- `OK @...` 不是在线状态证据。

### 17.2 主车 C 信号自动生成 EVENT

主车 `App_Update()` 在取得本拍 `BluetoothDebug` 信号或 KEY2 急停后执行：

```c
if (context->hasBluetoothSignal != 0U)
{
    CarLink_SendEvent(context->bluetoothSignal, NULL, 0U);
}
```

`CarLink_SendEvent(eventId, NULL, 0)` 构造载荷 `[eventId]`，消息类型为 `EVENT=0x20`。因此：

- 网页发 `C0`：主车先本地停车，同时向从车发事件 0。
- 主车按 KEY2：App 合成 C0，同样向从车发事件 0。
- 网页发 `C1..C255`：主车把相同编号发给从车。

### 17.3 从车处理 EVENT 的实际行为

从车 `App_HandlePeerMessage()` 当前写的是示例逻辑：

```text
eventId == 0
  -> MotionManager_Stop()
  -> Motor_StopAll()

eventId != 0
  -> Beep_Notify(1)

最后 -> CarLink_Send(ACK, [eventId], 1)
```

需要特别区分“代码注释想表达的用途”和“现行实际行为”：

- 事件 0 能立即停止从车运动层和电机硬件。
- 事件 0 没有写入从车 `context->bluetoothSignal`，所以不会直接调用从车的 `Mission_ResetToStart()`。
- 非零事件当前只鸣一声，不会启动从车 25H，也不会发布为从车 Mission 信号。

因此源码注释中的“一起启动/一起急停”目前只有硬件停车部分完整；“一起启动”和“从车 Mission 回到 WAITING”还没有真正接通。需要从车完整执行 C0 语义时，发 `@C0` 会在从车命令解析器中发布本地 C0，下一拍经过从车 App 和 Mission 的正常复位路径。

### 17.4 ACK 返回主车

从车对每个 EVENT 发 `ACK=0x30`，载荷第 0 字节是事件号。主车收到后向网页打印：

```text
PEER ACK 0
PEER ACK 7
```

现行 ACK 没有携带原 EVENT 帧序号，也没有超时重发、去重或请求表。因此它适合“尽力而为的状态提示”，不是严格的一次且仅一次事务协议。若事件会造成不可重复的机械动作，应增加请求 ID、重复检测和超时策略。

### 17.5 未知业务消息兜底

主车收到未识别的 CarLink 类型，不会静默丢弃，而是输出：

```text
PEER t=<type> n=<length> <payload hex...>
```

这便于先在从车添加新消息并观察原始载荷。但正式接入后仍应在 `App_HandlePeerMessage()` 增加明确 `case`，否则网页只能看到十六进制，不能驱动业务 UI。

## 18. 分支十五：从车 `0xAB` 二进制遥测透传

这一分支与 `RELAY_REPLY` 不同：从车遥测没有再包一层 CarLink `TYPE`，而是直接复用遥测帧，只把第一字节从 `0xAA` 改成 `0xAB`。

### 18.1 网页开启从车遥测

从车编译时 `Telemetry_Init()` 会强制把默认频率设为 0，避免上电就占用主车上行带宽。网页从车面板执行：

```text
@M63    从车选择 TL/LV/PL/TR/RV/PR
@G50    从车以 50 Hz 输出
```

两条命令先走第 16 章的 `RELAY_CMD` 链路。从车分别调用 `Telemetry_SetFieldMask(63)` 和 `Telemetry_SetRateHz(50)`，短 ASCII 回应以 `SLV OK ...` 返回。

### 18.2 从车产生 `0xAB` 帧

从车每拍 `Telemetry_Update()` 到达输出时刻后仍调用 `TelemFrame_Build()`，先构建普通 `0xAA 0x55` 帧。`Telemetry_Emit()` 在 `CAR_IS_SLAVE` 编译分支中改写：

```c
frame[0] = 0xABU;
Serial2_SendArray(frame, frameLength);
```

CRC 不覆盖 magic 两字节，所以只改首字节不会破坏校验。帧仍然是：

```text
AB 55 | VER | SCHEMA/SAMPLE | SEQ | LEN | PAYLOAD | CRC
```

### 18.3 主车只收齐和透传，不解释字段

主车 `CarLink_Update()` 从 Serial2 取出的每个字节会同时喂给两个状态机：

```text
CarLink_ParseByte(data)          识别 AA 55 控制帧
CarLink_TelemPassthruByte(data)  识别 AB 55 从车遥测帧
```

透传状态机读取到 LEN 后收齐 `payload + CRC`，随后调用：

```c
Serial1_SendArray(s_ptFrame, s_ptIndex);
```

它不把遥测字段转成结构体、不改序号、不重算 CRC。主车仅承担 UART2 到 UART1 的帧级转发。

### 18.4 网页最终解析

网页 `routeStream()` 识别 `0xAB 0x55` 后，先把帧首字节临时归一化成 `0xAA`，再送入独立的 `slaveParser`。因为 CRC 不含 magic，这个改写仍能通过 `TelemetryParser` 的 CRC 校验。

从车 schema、曲线、采样数组、录制数组都与主车独立；但物理带宽并不独立：

```text
从车 UART2 遥测 + CarLink 控制帧
          -> 主车 UART1 上行
          + 主车自身遥测 + ASCII 回应
```

两车频率和通道数之和过大时，Serial2 或 Serial1 DMA 环形缓冲都可能丢数据。网页显示的从车带宽条只是估算，不是流控协议。

### 18.5 从车板载捕获（议题已消失）

板载捕获模块已整体移除（见 15 节），`@X0` 不再存在，因此“从车实时遥测可用但板载捕获无法回传”这个历史限制自动消失。从车观测统一走 `@M/@G` 的 `0xAB` 透传路径。

## 19. 分支十六：`P` 与 K230Link 保留链路

### 19.1 当前运行结论

网页发 `P1` 时，UART1 命令解析仍会进入 `BluetoothDebug case 'P'`。但 `App_Init()` 中 `K230Link_Init()` 已被注释，`App_Update()` 中没有活动的 `K230Link_Update()`，UART2 正被 `CarLink_Init()` 占用。

静态变量上电为 0，`K230Link_IsReady()` 必然返回 0，所以当前结果固定为：

```text
ERR CAP NOLINK
```

这不是 K230 本次恰好没回应，而是当前固件根本没有运行 K230 状态机。

### 19.2 如果链路启用，READY 握手怎样工作

K230Link 与 CarLink 使用同一帧范式：

```text
AA 55 | 01 | TYPE | SEQ | LEN | PAYLOAD | CRC8
```

初始化时 TI 板生成一个固定的 `s_readySequence`。只要自己的 READY 尚未获确认，每 10 拍，也就是 100 ms 重发：

```text
TYPE=READY(0x01), SEQ=s_readySequence, LEN=0
```

收到对方 READY 后，TI 板记录 `s_peerReadyReceived=1`，并返回：

```text
TYPE=READY_ACK(0x02)
PAYLOAD=[对方 READY 的 sequence]
```

只有同时满足以下两个条件，`K230Link_IsReady()` 才为真：

```text
已经收到 K230 的 READY
并且 K230 的 READY_ACK 确认了 TI 自己的 READY sequence
```

这是一种双向就绪确认，不是单边收到任意数据就算在线。

### 19.3 K230 TARGET 上行分支

K230 发 `TARGET=0x10`，载荷固定 5 字节：

```text
valid:u8 | offsetX:int16_LE | offsetY:int16_LE
```

TI 仅在完整握手后接受该帧。`K230Link_HandleFrame()` 解析小端有符号偏移，保存帧序号并设置 `s_hasTarget=1`。上层调用 `K230Link_GetTarget()` 可读取最近目标。

当前 `K230Link_GetTarget()` 读取后不会清除 `s_hasTarget`，语义更接近“读取最近一次快照”，不是“弹出一次消息”。现行 App 和 25H 都没有调用它，所以即使单独恢复链路，目标也不会自动驱动车辆或云台。

### 19.4 `P<count>` 拍照请求分支

在完整启用的旧设计中，网页发 `P3` 后：

```text
BluetoothDebug case P
  -> 检查 count 1..20
  -> K230Link_IsReady()
  -> K230Link_RequestCapture(3)
  -> TYPE=CAPTURE(0x20), PAYLOAD=[3]
  -> s_capturePending=1
  -> 立即回 OK CAP REQ 3
```

K230 完成后返回：

```text
TYPE=CAPTURE_ACK(0x21)
PAYLOAD=ok:u8 + index:u16_LE
```

`K230Link_HandleFrame()` 保存 `ok` 和 TF 卡文件起始编号 `index`，清除 pending，并置 `s_captureAckPending`。旧 App ACK 处理块随后应输出：

```text
OK CAP <index>
```

或：

```text
ERR CAP FAIL
```

如果 100 拍，也就是 1 秒内没有收到 ACK，K230Link 会合成 `ok=0,index=0` 的失败结果。注意 `OK CAP REQ 3` 只表示请求发起，不表示照片已经落盘；最终结果必须看后续 `OK CAP ...`。

### 19.5 当前为什么不能简单取消一行注释

K230Link、CarLink、F32C 都直接调用 `Serial2_Init/ReadByte/SendArray`，共用 PA21/PA22。若同时更新两个解析器：

- 一个模块会先把 Serial2 RX 字节取走，另一个看不到。
- 三种协议可能互相把帧头当噪声或误同步。
- TX 帧会混在同一物理设备线上。
- HC05、K230、F32C 是三个不同对端，电气连接本身也不能这样复用。

正确恢复方式是给 K230 分配独立 UART/软件串口并建立 `Serial3`，随后一起恢复：

1. `K230Link_Init()`。
2. 每拍 `K230Link_Update(elapsedTicks)`。
3. `K230Link_PopCaptureAck()` 的 App 回应块。
4. K230 端匹配协议的程序。仓库当前没有 README 提到的 `uart_io.py`。
5. 若 TARGET 要参与业务，再增加明确消费者和失效超时。

## 20. 分支十七：当前真正上电运行的 25H 物理任务

这一分支不是网页命令，而是 `main.c` 当前装载的比赛状态图：

```c
App_Init();
Mission_Init(Accomplish25H_GetMissionGraph());
Interrupt_Enable();

for (;;)
{
    if (App_Update(&updateContext) != 0U)
    {
        Mission_Update(&updateContext);
    }
}
```

### 20.1 初始状态 WAITING

`Mission_Init()` 验证状态图后进入 `ACCOMPLISH_25H_STATE_WAITING`，调用 `Accomplish25H_WaitingEnter()`：

```text
s_nextTurnTargetDeg = 0
s_headingReferenceCaptured = 0
```

WAITING 的 `onUpdate` 始终返回 RUNNING，使 Mission 每拍检查可打断转换。车辆不启动，等待 KEY1 的按下沿。

### 20.2 KEY1 怎样启动任务

App 每拍读取按键并计算：

```c
pressedEdges = keyMask & ~s_previousKeyMask;
```

KEY1 是 bit0。只有从松开到按下那一拍，`Accomplish25H_ConditionStart()` 才返回真；一直按住不会重复启动。

Mission 发现 WAITING 的 INTERRUPT 转换成立后，依次执行：

```text
Mission_CallExit(INTERRUPTED)
MotionManager_Stop()
Mission_EnterState(LINE)
  -> Accomplish25H_LineEnter()
```

### 20.3 首次 LINE：保存航向基准并启动巡线

首次进入 LINE 时：

```text
Heading_IsReady() == 0
  -> onEnter ERROR
  -> Mission_SetError()
  -> MotionManager_Stop()

Heading 已就绪
  -> s_nextTurnTargetDeg = Heading_GetYaw()
  -> s_headingReferenceCaptured = 1
  -> MotionManager_StartLine(200 mm/s)
```

底层调用链是：

```text
MotionManager_StartLine
  -> MotionLine_Start

每个 App 拍：
MotionManager_Update
  -> MotionLine_Update
  -> Graydetect_GetState
  -> 计算五路离散线误差和变化率阻尼
  -> 生成左右目标轮速
  -> MotionWheel_Update
  -> 左右轮 PI + 前馈
  -> Motor_SetPWM
```

### 20.4 左侧双黑线怎样切换到 FORWARD

LINE 仍在运行时，Mission 每拍检查 `Accomplish25H_ConditionLeftMarker()`：

```c
(Graydetect_GetState() & 0x03U) == 0x03U
```

也就是最左侧 bit0 和左内侧 bit1 必须同时为黑。这个条件不做多拍确认，在同一拍立即打断 LINE，避免巡线控制器继续把双黑线当普通左偏。

进入 FORWARD 前 Mission 先调用 `MotionManager_Stop()`，再调用：

```c
MotionManager_StartForward(150, 200.0f, 0.0f);
```

FORWARD 由 `MotionStraight` 完成定距速度规划、航向保持、轮速闭环，最终目标速度减到 0；MotionManager 还执行短暂 PWM 释放和主动刹车阶段。

### 20.5 FORWARD 完成后怎样转向

FORWARD 的 `onUpdate` 只调用 `Mission_GetMotionActionStatus()`。动作完成后，NORMAL 转换无条件进入 TURN。

每次进入 TURN：

```c
s_nextTurnTargetDeg += -90.0f;
MotionManager_TurnTo(s_nextTurnTargetDeg, 80.0f);
```

假设 KEY1 启动时连续航向是 12°，目标依次为：

```text
-78° -> -168° -> -258° -> ...
```

这里用的是连续绝对角 `TurnTo()`，不是从当前角再转一次 `TurnBy()`。Nav 根据绝对误差生成左右反向轮速，进入容差并稳定后完成。

### 20.6 TURN 完成后继续循环

TURN 正常完成后无条件进入 LINE。由于 `s_headingReferenceCaptured` 已经是 1，后续 LINE 不会覆盖启动基准，只重新调用 `MotionManager_StartLine(200)`。

完整循环为：

```text
WAITING
  -- KEY1 edge --> LINE
  -- 左侧两灰度同时黑 --> FORWARD 150 mm
  -- 定距完成 --> TURN 到下一个 startYaw - 90° * n
  -- 转向完成 --> LINE
  -- 再次检测标志 --> FORWARD -> TURN -> LINE ...
```

### 20.7 丢线和错误怎样结束

如果 LINE 没有遇到左侧标志，而 `MotionLine` 连续丢线达到公共阈值后正常完成，LINE 的 NORMAL 兜底转换进入 WAITING，停车并清除本轮航向基准。

任一状态启动 MotionManager 失败、运动更新返回 ERROR 或 `MotionManager_GetError()` 非 NONE，Mission 进入 ERROR 并停车。ERROR 不会自行恢复；C0 会走 `Mission_ResetToStart()` 回到 WAITING。

### 20.8 C0、KEY2 与网页命令对 25H 的影响

- `C0`：App 当拍先 `MotionManager_Stop()` 和 `Motor_StopAll()`，随后 Mission 看到信号 0，重置到 WAITING。
- KEY2：App 合成相同的 C0，因此效果与本地主车 C0 相同。
- `C1..C255`：25H 没有对应条件，不能启动任务。
- F/T/N/J 等网页运动：25H 处于 WAITING 时可能启动独立 MotionManager 动作；Mission 的 WAITING 本身不知道这条命令的业务含义。比赛流程和手动调试不要并行使用。
- `@...`：只影响从车本地命令解析，不改变主车 25H 状态图。

## 21. 网页复合使用分支

前面章节按单条命令解释。本节按用户点击一次按钮后真实发生的命令序列解释。

### 21.1 点击“连接”

`connect()` 的完整顺序是：

```text
navigator.serial.requestPort()
  -> port.open(115200, 8N1)
  -> writer = port.writable.getWriter()
  -> 清 paramCache
  -> readLoop() 开始读二进制和文本
  -> applyFocusedTelemetrySelection(true)
     -> G0
     -> M<preset.mask>
     -> Q
     -> G<安全频率>
  -> 300 ms 后 K?
```

先 `G0` 是为了避免旧 schema 的 SAMPLE 在切换掩码时继续混入。`M` 改掩码后再问 `Q`，因为安全频率取决于新帧长度；最后才用 `G` 开流。`K?` 延迟 300 ms 是为了让上电 READY 横幅和前面的设置先完成。

每次连接都会清空网页参数缓存，不沿用上一块板的值。参数本身仍由固件上电默认值决定，浏览器保存值不会自动写回，除非点击“应用已存参数”。

### 21.2 切换调参对象/阶段

`applyFocusedTelemetrySelection()` 把请求串行化，并用 generation 防止断开重连后旧任务继续发送。一次切换也是：

```text
G0 -> M<新掩码> -> Q -> G<按固件上限裁剪后的频率>
```

四种调参预设的激励是：

| 页面对象 | 激励命令 | 正常停止命令 | 典型观测 |
|---|---|---|---|
| 轮速 PI | `W<速度>` | `W0` | TL/LV/PL/TR/RV/PR |
| 直线航向 | `F<距离>` | `C0` | yaw、距离、轮速 |
| 转向 | `T<角度>` | `C0` | navE、yaw、轮速 |
| 巡线 | `N<速度>` | `N0` | lerr、轮速、yaw |

### 21.3 点击“开始试验”

`startSession()` 当前执行：

```text
校验幅值和定时时长
  -> 清网页终端和实时样本
  -> 快照当前参数表
  -> sendAndWait(excitation)
  -> 等待 OK/ERR
  -> 定时试验启动 stopTimer
  -> 所有试验启动 30 秒安全 guardTimer
```

它不会在开始时重新发送 `M/G`，而是使用前面焦点切换已经设置好的流；也不会发送 `X<mask>`。指标默认来自实时二进制遥测。

对于 F/T，固件立即 `OK` 只代表动作已启动。网页后续根据实时样本判断动作曾经 ACTIVE 且回到完成状态，再留 0.5 秒尾部数据。对于定时 W/N，定时器到期后先发 W0/N0，确认停车回应，再等待尾部数据。

### 21.4 会话中急停或超时

`stopSession()` 会清除定时器，调用网页全局 `emergencyStop()`，再完成本次记录。急停发送去重后的序列：

```text
<当前预设 stopCmd，若存在>
J0/0
@J0/0
W0
N0
C0
U0
```

这一序列刻意包含多种模式的停止命令。前面的命令可能因模式不匹配返回 `ERR BUSY`，但主车最终的 `C0` 是全局停止。`U0` 再把开环 PWM 置零。

从车方面，`@J0/0` 只能在 DRIVE/IDLE 时完整退出驾驶；主车 C0 还会生成 EVENT 0，使从车 `MotionManager_Stop()` 和 `Motor_StopAll()`。但如第 17 章所述，EVENT 0 当前不复位从车 Mission。若需要从车也严格回到 WAITING，急停序列应后续补 `@C0` 或修正 EVENT 0 的 App 语义。

### 21.5 键盘同时驾驶两车

网页固定映射：

```text
W/A/S/D  -> 主车 J<left>/<right>
方向键   -> 从车 @J<left>/<right>
Esc      -> 两套按键状态清空 + 全局急停序列
```

油门和转向在网页中混合：

```text
base = throttle * speed
bias = steer * turn
left  = clamp(base + bias, -800, 800)
right = clamp(base - bias, -800, 800)
```

只有左右结果和上一帧不同才发送，减少重复命令。松键会重新计算并下发；所有键都松开时发 `J0/0` 或 `@J0/0`。浏览器失去焦点时也清空状态，防止收不到 keyup 后持续行驶。

### 21.6 录制、标记和 CSV 导出

网页录制在浏览器侧完成（板载捕获已移除，见 15 节）：

- `recording.samples` 收集主车实时 SAMPLE。
- `recording.samplesSlave` 收集从车 `0xAB` SAMPLE。
- 两者共用浏览器开始时间轴 `t` 和当前场景标记。
- 停止录制后会生成 summary，最多保留最近 6 次会话并持久化到浏览器存储。
- “整段 CSV”对主从分别导出文件；“按标记分段”按连续标记区域切分，少于 5 个样本的段不导出。

CSV 是网页对已解析二进制样本的导出格式，不表示固件当前发送 ASCII CSV。

### 22.1 25E 状态图

`Accomplish/25E.c/.h` 是完整但未装载的另一套任务图。若把 main 改为 `Accomplish25E_GetMissionGraph()`，其流程为：

STRAIGHT 的转换表先检查入线条件，再放无条件“走满距离回等待”的兜底，因此同一拍既检测到黑线又完成距离时，黑线优先。25E 同样要求 Heading 可用，错误进入 ERROR，C0 才能复位。

### 22.2 TestApp

`Application/Core/TestApp.c` 是裁剪过的硬件测试入口：

```text

C0/KEY2 类停止时停 MotionManager、Motor 和 Gimbal
```

它没有初始化当前整车 App 的 Graydetect、Heading、Odometry、Telemetry、CarLink 和 OLED 流程。`manualMotorEnabled=0` 会拒绝 L/R/U，但保留 C0 和 O/D。

当前 `main.c` 没有调用 `TestApp_Init/TestApp_Update`。切换到 TestApp 属于更换应用入口，不是网页命令可以进入的运行分支。

### 22.3 F32C/Gimbal

F32C 协议使用 UART2：

```text
0x7A | address | function | payload | BCC | 0x7B
```

`F32C_SendCommand()` 通过 Serial2 发送，并按手册在相邻多电机命令间延时至少 1 ms。`F32C_PopFeedback()` 从 Serial2 搜索固定 9 字节反馈帧，校验帧头、帧尾、地址、类型和 BCC。

`Gimbal_Init()` 初始化 F32C 后进入 DISABLED；`Gimbal_Enable()` 对地址 1/2 依次执行使能、T 型多圈模式、加速度和速度配置。`Gimbal_SetTargetAngles()` 下发两个轴的多圈角度。`Gimbal_Update()` 每 30 ms轮流请求一轴总角度反馈；某轴 1 秒无反馈会失能两轴并进入 ERROR。两轴都连续两次处于目标 ±2° 才算到位。

当前 App 中 `Gimbal_Update()` 和失能调用被注释，且没有 `Gimbal_Init()`，因为 UART2 已给 CarLink。网页 O/D 控制的是 TIMA0 上的普通 PWM 舵机，不是 F32C Gimbal。

### 22.4 Brushless_Motor_Test Mission

该保留状态图原本用于双轴 F32C 云台：

```text
STOPPED 上电只自动启动一次
  -> ZERO：两轴目标 0°
  -> Y_TO_180：X 每段继续累加 180°，Y 到 180°
  -> Y_TO_0：X 再累加 180°，Y 回 0°
  -> 两状态循环
KEY2/C0 -> STOPPED 并失能
反馈错误 -> ERROR 并失能
```

只把 `Mission_Init()` 参数换成这个图仍不够，因为当前 App 没有初始化和更新 Gimbal。要恢复它，需要同时设计独立 UART、恢复 Gimbal 生命周期，并确认 TestApp 与 Mission 的组合入口。

## 23. 文本回应和错误字典

### 23.1 通用解析错误

| 回应 | 产生条件 | 命令是否执行 |
|---|---|---|
| `ERR COMMAND` | 裸数字，或分派到未知命令 | 否 |
| `ERR FORMAT` | 普通命令缺数字，例如裸 F | 否 |
| `ERR CHARACTER` | 当前命令遇到不允许字符 | 否，当前半条命令被复位 |
| `ERR RANGE` | 数值不在该命令范围 | 否 |
| `ERR BUSY` | MotionManager 正被不兼容模式占用，或手动 PWM 被禁用 | 否 |
| `ERR STOP PENDING` | 单槽任务邮箱已有最高优先级 C0，普通 C 信号不能覆盖 | 否 |

### 23.2 MotionManager 错误码

F/B/T/A/W/N 可能回 `ERR MOTION <n>`：

| n | 枚举 | 含义 |
|---:|---|---|
| 1 | `INVALID_ARGUMENT` | 底层再次判定参数非法 |
| 2 | `NOT_CONFIGURED` | MotionManager 或所需模块没有正确初始化 |
| 3 | `SENSOR_NOT_READY` | 依赖传感器未就绪；F/B/T/A 常见为 Heading/MPU 不可用 |
| 4 | `START_FAILED` | 下层动作启动失败 |

0 是成功，不会显示为错误。J 使用单独文本 `ERR J MOTION`，没有把具体 Result 数字带出。

### 23.3 J、K 与遥测

| 回应 | 含义 |
|---|---|
| `ERR J FORMAT` | 不符合 `<left>/<right>`，或文本缓冲溢出 |
| `ERR K FORMAT` | K 参数格式非法或缓冲溢出 |
| `ERR K ID` | 参数 ID 不是 1..26 |
| `ERR K RANGE MIN=x MAX=y` | 写值超出该参数边界 |
| `ERR RANGE MAX=n` | G 频率超过当前掩码允许的上限 |
| `ERR X MASK MAXCH=8` | X 掩码非法、为 0、超过 12 位、超过 8 通道，或正在 DUMPING 时重新 arm |
| `ERR X EMPTY` | X0 时没有样本，或已经在 dump |

### 23.4 航向标定

| 回应 | 含义 |
|---|---|
| `ERR Z OFFLINE` | Z2 前后 Heading 都未就绪 |
| `ERR Z CALIBRATING` | 正在 E/Y 尺度标定，拒绝 Z2 |
| `ERR CAL OFFLINE` | E1 时 Heading 未就绪 |
| `ERR CAL IDLE` | 未 E1 就执行 Y |
| `ERR CAL SMALL` | 累计原始转角绝对值不超过 1°，拒绝计算尺度 |

### 23.5 CarLink 与 K230

| 回应 | 准确语义 |
|---|---|
| `ERR @ EMPTY` | `@` 后没有命令 |
| `ERR @ FORMAT` | `@` 后超过 23 字符 |
| `ERR @ LINK` | `CarLink_SendCommand` 返回失败；当前路径不用于表示 peer 离线，底层 TX 满也不会触发它 |
| `OK @...` | 主车接受了转发请求，不是从车执行成功 |
| `SLV OK.../SLV ERR...` | 从车命令解析器的真实回应 |
| `ERR CAP NOLINK` | K230 双向 READY 未完成；当前固件因 K230 停用而固定出现 |
| `ERR CAP BUSY` | K230 已有未完成拍照请求，或请求入口失败 |
| `OK CAP REQ n` | 只表示拍照请求已发起 |
| `ERR CAP FAIL` | K230 回失败或 1 秒超时；对应 App 处理块当前被注释 |

### 23.6 回应的时间语义

看到 OK 时要先判断它属于哪一级：

```text
F500 -> OK
```

表示 MotionManager 已成功启动，不表示 500 mm 已经走完。

```text
P3 -> OK CAP REQ 3 -> 稍后 OK CAP <index>
```

第一行是请求开始，第二行才是业务完成；但当前 P 分支停用。

```text
@F500 -> OK @F500 -> 稍后 SLV OK
```

第一行来自主车，第二行来自从车，且两行都只表示动作启动成功。F 动作完成本身没有 ASCII DONE 回包，需由遥测或上层状态判断。

| G 是“CSV 输出频率” | 当前固件输出 `SCHEMA/SAMPLE` 二进制帧，CSV 只在网页导出阶段生成 |
| `Serial1_SendByte()` 阻塞，按 20% 带宽预算 | 当前 Serial1 是 TX 环形缓冲 + DMA，Telemetry 用 70% 预算 |
| `X` 板载捕获可用 | 模块已整体移除，`X` 命令不再存在，见 15 节 |
| K230 端有 `uart_io.py` 测试入口 | 当前仓库没有该 Python 文件 |
| CarLink 文档说网页有“主车/从车/同时”目标下拉框 | 当前网页明确固定 WASD 主车、方向键从车，没有这套通用目标选择分支 |
| EVENT 可实现一起启动 | 当前从车非零 EVENT 只鸣笛；事件 0 只停运动和电机，不发布 Mission 信号 |

`docs/主从通信-CarLink说明.md` 对帧格式、`@` 回传和 `0xAB` 遥测的主体描述是有效的，但其中 UI 交互和 EVENT 业务语义仍有上述偏差。

## 25. 怎样安全增加新命令、消息或通道

### 25.1 增加一条 UART1 ASCII 命令

假设增加 `S<number>`：

1. 在 `BluetoothDebug_IsCommand()` 增加 `S`，否则字符会走 `ERR CHARACTER/COMMAND`。
2. 若参数只是带符号整数，可复用通用 magnitude；若像 J/K 一样有分隔符或小数，必须增加独立文本收集规则。
3. 在 `BluetoothDebug_ExecuteCommand()` 增加 `case 'S'`，先在 int32 范围检查，再转换到窄类型，避免 `256 -> uint8_t 0` 这种截断。
4. 明确忙状态策略：拒绝、同模式更新，还是全局打断。不要让普通调试命令无意中打断 Mission。
5. 明确停止命令是否只停自己的模式；全局停车仍统一走 C0。
7. 回应必须是一行稳定的 `OK ...` 或 `ERR ...`，同步更新网页的 reply matcher 和错误说明。
8. 再检查 `@S...`：载荷是否不超过 23 字符、从车回应是否不超过 32 字节。

### 25.2 增加一种 CarLink 业务消息

1. 在 `CarLink_MsgType_t` 分配未占用 TYPE；避开 `0x01` 心跳、`0x10/0x11` relay、`0x20` event、`0x30` ack。
2. 发送端调用 `CarLink_Send(type, payload, length)`，长度必须不超过 32。
3. 在接收角色的 `App_HandlePeerMessage()` 增加 `case`。
4. 决定消息是否需要 ACK、请求 ID、超时、重发和重复抑制。现有通用 ACK 不自动提供这些保证。
5. 检查 RX 队列只有 6 项，满时丢最旧；高频状态流不应逐条塞业务队列，适合另建最新值缓存或专用流。
6. 检查 `Serial2_SendArray()` 的失败是否需要向业务层传播。关键指令不能继续沿用“TX 丢帧但上层仍返回成功”的现状。
7. 不要使用 `0xAB 0x55` 作为普通控制帧头，它已保留给从车遥测透传。

### 25.3 增加遥测通道

1. 只能在现有 12 位之后追加新 bit，不能重排已发布位。
2. 在 `Telemetry.c` 的 `s_channels[]` 表增加名字、单位和读取函数。
3. 扩展 `TELEMETRY_CH_ALL`。
4. 检查 `TELEM_FRAME_MAX_PAYLOAD/MAX_BYTES` 是否仍容纳全通道 schema 和 sample。
5. 网页 `CH`、`CH_LIST`、显示单位、预设掩码必须同步。
6. 重新检查 `Telemetry_GetMaxRateHz()` 的帧长预算。
7. 主车与从车 parser 都依赖同一位序；至少验证主 `0xAA` 与从 `0xAB` 两条路径。

### 25.4 增加新的物理通信设备

不要再让 K230、F32C、CarLink 共享 Serial2 消费接口。新增 UART/软件串口时应完整建立：

```text
SysConfig PinMux/波特率
RX 中断和 RX 环形缓冲
TX DMA 通道和 TX 环形缓冲
Serial3_Init/ReadByte/SendArray
独立协议 Update
App_Init/App_Update 生命周期入口
```

同时检查 ISR 名称、DMA 完成中断、缓冲满策略、线序、电平、共地和设备供电。源文件存在但没有 Init/Update 调用，功能仍然不可达。

### 25.5 增加比赛 Mission

新题目应在 `Accomplish/<题号>.c/.h` 定义独立静态状态图：

- `onEnter` 只启动一次 MotionManager 动作。
- `onUpdate` 只查询动作状态，不重复更新底层控制器。
- 条件函数读取 `App_UpdateContext` 或传感器公共接口。
- 中断转换与正常完成转换分清；数组顺序就是优先级。
- ERROR 状态必须安全停车，C0 仍由通用 Mission 负责全局复位。
- 在 `main.c` 只替换 `Mission_Init()` 的图入口，不把题目判断散落进 App。

## 26. 推荐阅读顺序和最终心智模型

第一次读工程，建议按下面顺序：

1. `main.c`：确认当前 App 和 Mission 到底是哪一个。
2. `Application/Core/App.c`：掌握每个 10 ms 拍的模块顺序和全局停止位置。
3. `Hardware/Comms/Serial.c`：理解 UART 中断只收字节、DMA 只发字节。
4. `Application/Comms/BluetoothDebug.c`：理解 23 个命令和 `@` 的文本分派。
5. `Application/Control/MotionManager.c`：理解同一时刻谁拥有双轮。
6. 根据命令进入 `MotionStraight`、`MotionLine`、`Nav` 或 `MotionWheel`。
7. `Application/Comms/CarLink.c`：理解第二块板的封帧、队列和透传。
8. `Application/Debug/Telemetry.c`、`TelemFrame.c`：理解上行二进制数据。
9. `Accomplish/25H.c` 与 `Application/Mission/Mission.c`：理解当前自动比赛流程。
10. 最后读 K230、F32C、25E、TestApp 等保留代码，避免把“存在”误认为“正在运行”。

整个项目可以压缩成四条主干：

```text
网页控制：Web Serial -> UART1 -> BluetoothDebug -> MotionManager/Servo/Param

双车控制：网页 @命令 -> 主车 BluetoothDebug -> CarLink -> 从车 BluetoothDebug

观测回传：模块状态 -> Telemetry -> 二进制帧 -> 网页 parser/曲线/CSV

比赛任务：KEY/传感器 -> Mission(25H) -> MotionManager -> MotionWheel -> Motor
```

判断任意功能是否真的可用时，依次问四个问题：

```text
入口是否被 main/App 调用？
接收字节是否有 ISR/Update 消费？
解析后的结果是否有业务模块读取？
成功回应表示“已开始”还是“已完成”？
```

这四个问题能解释本工程里大多数“代码明明存在，为什么实车没有反应”的情况。
